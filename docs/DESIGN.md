# Econet 설계 문서

친구들끼리 쓰는 Paper 서버용 경제 플러그인의 게임 설계와 결정 사항을 정리한 문서다.
코드 규칙은 루트의 `CLAUDE.md`를, 게임 규칙과 결정 이유는 이 문서를 기준으로 한다.

## 1. 화폐

| 항목 | 값 | 비고 |
|---|---|---|
| 이름 | 듄 | 설정 파일로 변경 가능 |
| 코드 | DYN | 고정 |
| 표시 | `12,500듄` | 로그·설정·명령어에서는 `12500 DYN` |
| 단위 | 정수 | 내부 가격 계산만 소수, 지급액은 내림 |

- core는 화폐 이름과 코드를 모른다. 표시는 paper 레이어의 포매터가 설정을 읽어서 처리한다.

```yaml
currency:
  name: "듄"
  code: "DYN"
  format: "{amount}{name}"
```

## 2. 장부 원칙

돈은 생기거나 사라지지 않고 계좌 사이를 이동만 한다. 모든 계좌 잔액의 합은 항상 0이다.

### 계좌

| 계좌 | 역할 | 음수 허용 |
|---|---|---|
| `Player(uuid)` | 플레이어 예금 | X |
| `Government` | 정부 금고. 매입·상점·보험의 상대 | X |
| `Issuance` | 발행 계좌. 잔액의 부호를 뒤집으면 서버 전체 통화량 | O (유일) |
| `CashPool` | 현금 유통 계좌. 잔액 = 세상에 풀려 있는 금화 총액 | X |

### 경로 규칙

- **Mint / Burn**: `Issuance ↔ Government` 사이에서만 쓴다. Issuance도 Mint/Burn으로만 거래한다(양방향 강제).
- **CashOut / CashIn**: `CashPool`과 짝지어 강제한다. 상대는 `Player` 또는 `Government`.
  - Government를 허용하는 이유: 서버 상점이 금화를 받을 때 거래 한 건으로 끝내고, 이벤트용 금화 발행이 관리자 개인 계좌를 거치지 않게 하기 위해서.
- 나머지 TxKind는 분류용 라벨이다. 경로를 강제하지 않는다.
- 위반 시 `InvalidRoute`.

### 무결성

- 서버 시작 시 검사: (1) 전체 잔액 합 == 0, (2) 저장된 잔액 == 장부 재생 잔액.
- `CashPool` 음수 금지는 **금화 복사(듀프) 감지 장치**를 겸한다. 인출된 것보다 많은 금화가 입금되려 하면 거래가 막히고, 그 자체가 복사의 증거다.

## 3. 정부

- 당분간 정부 = 관리자(OP). 계좌(Government)와 조작 주체(Actor.Admin)를 분리해 두어 나중에 선출직 등으로 교체할 수 있게 한다.
- 관리자 개입도 잔액 직접 수정이 아니라 거래로 남긴다. 모든 개입이 장부에 투명하게 보인다.
- 테스트 단계에서는 정부가 자유롭게 발행할 수 있다.
- 권한: `econet.admin`.

## 4. 돈이 들어오는 문 (Faucet)

### 시작 자금

- **없음.** 신규 플레이어는 0듄에서 시작한다.
- 서버를 열 때 정부 금고에 초기 예산을 한 번 발행한다.

### 정부 매입

- 원칙: **직접 캤다는 증거가 되는 아이템만 받는다.** 원석은 광석 채굴로만 나오므로 농장 산출물을 걸러 낸다.
- **정부 예산 안에서만 매입한다.** 금고가 비면 매입이 멈춘다. 이 시점이 발행 여부를 판단할 신호다.

| 분류 | 품목 | 기준가 (듄) |
|---|---|---|
| 광물 | 석탄, 구리 원석, 청금석, 석영 | 0.5 |
| | 레드스톤 | 0.3 |
| | 철 원석 | 2 |
| | 금 원석 | 5 |
| | 다이아몬드 | 10 |
| | 고대 잔해 | 30 |
| 몹 드롭 | 뼈, 실, 화약, 썩은 살점 | 0.2 |
| | 엔더 진주 | 1 |
| | 블레이즈 막대 | 1.5 |
| 작물 | 밀, 감자, 당근, 비트 | 0.1 |

**제외 품목과 이유**

- 에메랄드: 주민 거래로 무한히 나온다.
- 모든 주괴·조각·블록: 철 골렘 농장, 좀비 피글린 금 농장의 산출물이다. 블록은 원석 압축 우회로다.
- 사탕수수, 다시마, 호박, 수박: 완전 자동 농장이 너무 쉽다.
- Econet 금화 태그가 붙은 아이템: 실수로 액면가보다 싸게 파는 것을 막는다.

**동적 가격**

- 품목별로 서버 전체 판매량이 쌓일수록 가격이 내려간다.
- 판매가 없으면 하루에 걸쳐 기준가로 회복된다.
- 바닥 가격은 기준가의 20%.
- 내부 가격은 소수로 계산하고, 한 번의 판매에서 최종 지급액만 내림한다. 끝전은 정부에 남는다.
- 몹 드롭과 작물 가격은 서버 오픈 후 약 일주일간 장부를 보고 조정한다.

### 몹 현상금

- 보스급(위더, 엘더 가디언, 습격 대장 등)에만 정부가 현상금을 지급한다.
- 일반 몹 처치에는 현상금이 없다. 일반 몹 드롭은 정부 매입의 동적 가격으로 처리한다.
- 몹은 금화를 드롭하지 않는다.

## 5. 돈이 나가는 문 (Sink)

- **플레이어 간 송금에는 세금이 없다.** 통화량을 늘리지 않는 건강한 거래를 억누르지 않기 위해서.
- **정부 상점**으로 시작한다: 이름표, 안장, 경험치 병, 구하기 귀찮은 건축 자재(점토, 사암, 산호 등).
- 텔레포트·땅 보호 비용은 미정. 서버 운영 후 친구들이 실제로 귀찮아하는 것을 보고 정한다.

### 사망 보험

- 서버 기본값은 **keepInventory 꺼짐**.
- 보험 가입자는 사망 시 보험료가 예금에서 정부로 빠지고 인벤토리를 지킨다.
- **보험이 있어도 금화는 떨군다.** 현금은 위험하고 예금은 안전하다는 구분을 유지하기 위해서.
- 보험료는 서버 운영 후 장부를 보고 정한다.

## 6. 현금 (금화)

| 아이템 | 액면 | 베이스 아이템 |
|---|---|---|
| 철화 | 1듄 | 철 조각 |
| 금화 | 10듄 | 금 조각 |
| 다이아화 | 100듄 | 다이아몬드 |

- 진짜 아이템을 베이스로 쓰고 `custom_data`(PersistentDataContainer) 태그로 구분한다. 리소스팩 없이 동작한다.
- 반짝임 효과와 이름을 붙여 일반 아이템과 겉으로 구분되게 한다.
- 모루로는 태그를 붙일 수 없으므로 서바이벌에서 위조할 수 없다.
- 금화를 조합·제련 재료로 써서 날리는 것은 본인 책임이다. 장부에서는 CashPool에 남아 조용히 소각된 것으로 처리된다.
- 인출(CashOut)과 입금(CashIn), 잔돈 교환은 명령어로 처리한다.

### 현금이 존재하는 이유

예금과 달리 금화는 아이템이라서 예금으로는 못 하는 일이 가능하다.

- 깔때기·상자·레드스톤과 엮어 플러그인 없이 자판기를 만들 수 있다.
- 손으로 건네면 장부에 기록이 남지 않는다. 비밀 거래, 선물, 숨긴 비상금.
- 정부가 이벤트 보상으로 맵에 숨길 수 있다.

## 7. 구조

```
core   순수 코틀린. Paper/Vault 의존 없음. Amount, Balance, AccountId, Transaction, Ledger
storage SQLite. 잔액과 장부를 함께 저장하고, 거래 기록과 잔액 변경을 DB 트랜잭션 하나로 묶는다
paper  명령어, 이벤트, 포매터, 설정, (나중에) Vault 어댑터
```

- Vault의 `Economy`는 `double` 기반이라 core에 들이지 않는다. 필요해지면 paper 쪽 어댑터로 변환한다.
- 코어 계산은 Rust 등 네이티브로 옮기지 않는다. 병목은 계산이 아니라 I/O이고, JNI 경계 비용과 배포 복잡도만 늘어난다.

## 8. 저장소

- SQLite 파일 하나. 테이블은 `accounts`(잔액)와 `transactions`(장부).
- DB 접근은 **직접 JDBC**. 쿼리가 몇 개 안 되고, SQL이 그대로 보여서 읽기 쉽다. Exposed는 이 규모에 비해 무겁다.
- **거래 한 건 = DB 트랜잭션 한 번.** 장부 기록과 두 계좌 잔액 변경을 함께 커밋한다. 실패 시 되돌릴 메모리 상태가 없다.
- **DB에 먼저 쓰고, 성공하면 메모리 캐시를 갱신한다.** 잔액 조회는 캐시에서 한다.
- 모든 쓰기는 전용 스레드 하나에서 처리한다. 메인 스레드를 막지 않고, 거래 직렬화 원칙을 유지한다.
- 거래 번호는 SQLite AUTOINCREMENT.

### 무결성 검사

- **장부가 진실이다.** 잔액 테이블은 장부를 빠르게 읽기 위한 캐시일 뿐이다.
- 서버를 자주 재시작하지 않으므로 시작 시 검사만으로는 부족하다.
  - 서버 시작 시 + 주기적으로(하루 한 번) 비동기 실행.
  - 관리자 명령어로 즉시 실행 가능.
- 거래는 항상 같은 금액을 옮기므로 장부 자체는 합이 0이 깨질 수 없다. 따라서 검사 실패는 사실상 **저장된 잔액 ≠ 장부 재생 잔액** 한 종류다.
- 실패 시:
  1. 모든 거래를 잠근다(잔액 조회는 허용). 관리자에게 경고한다.
  2. 관리자 명령어로 계좌별 차이를 확인한다.
  3. 복구 명령어 한 번으로 잔액 테이블을 장부 재생 결과로 덮어쓰고 잠금을 푼다.

## 9. 관리자 도구

### 인벤토리 열람

- 접속 중인 플레이어: 인벤토리와 엔더상자를 관리자 화면에 실시간으로 연다.
- 오프라인 플레이어: `playerdata/<uuid>.dat`를 읽어 인벤토리와 엔더상자(`EnderItems`)를 **읽기 전용**으로 연다.
  - 수정 중 해당 플레이어가 접속하면 서버가 파일을 덮어써 수정 유실이나 아이템 복사가 생길 수 있어서.
  - NBT를 아이템으로 변환하는 방법은 서버 버전에 맞춰 구현 시점에 확인한다.
- 금화 집계: 모든 플레이어의 인벤토리와 엔더상자에 있는 금화를 세어 CashPool 잔액과 비교한다. 월드 상자는 세지 않으므로 참고용 수치다.

### 스냅샷과 백업

- 주기적으로 **플레이어 데이터와 `econet.db`를 같은 시점에 함께** 백업한다.
  - 둘을 따로 복구하면 장부와 실제 금화가 어긋난다. 예: 인벤토리만 과거로 돌리면 이미 입금된 금화가 다시 생긴다.
- 스냅샷 간 차이로 사고 시점 전후 누가 무엇을 얻었는지 추적한다.
- 원칙: 스냅샷은 **사고 대응용**이다. 손으로 건넨 금화는 기록되지 않는다는 현금의 성격(6장)을 해치지 않도록, 평상시 감시나 공개 조회에 쓰지 않는다.
